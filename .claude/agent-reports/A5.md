## What I built

### Scanner (`impl/scanner/`)
- `PlatformScannerService` — the real `ScannerService`. `supportsCamera` is true on Android, iOS, macOS and Web; on Windows/Linux `scan()` opens the keyboard-wedge dialog straight away.
- `ScanPage` — full-screen `mobile_scanner` preview with torch (hidden when the camera has none), camera switch, a scan-window cutout, click + haptic on a hit, and a permanent "enter the code by hand" way out. Formats: EAN-13, EAN-8, UPC-A, UPC-E, Code 128, QR.
- `StableCodeDetector` — pure Dart; a code is returned only after the same value is read twice, which kills the occasional camera misread.
- `KeyboardWedgeDialog` — focused field a USB/Bluetooth scanner types into and submits with Enter; whitespace is rejected and the field stays LTR in an Arabic UI.
- Camera denied / no camera / camera failed each get their own translated explanation plus a manual-entry button (`ScanPage`'s `errorBuilder`).

### Notifications (`impl/notifications/`)
- `LocalNotificationService` — the real `NotificationService`. Localised title/body read **at send time**, so the text follows the language in use. Throttle: at most one notification per product **per level** per hour (`NotificationThrottle`, driven by the injected `Clock`). A blocked or failed send does not consume the window. Notification id is stable per product+level, so a newer notice replaces the older one instead of stacking.
- `LocalNotificationsBackend` — the only file that touches `flutter_local_notifications`: Android channel `low_stock` ("Low stock", high importance), Darwin settings with **no** permission prompt at start-up, Linux, Windows toast identity (`appName` and `com.shelfwise.<brandId>` from the brand config), web via the plugin's service worker. `requestPermission()` is only ever called from a user tap (dev page today, A1/A4 screens later) — the web requirement.
- Taps deep-link to `/alerts`: `notificationServiceProvider` subscribes to `service.taps` and calls `appRouter.go(route)`. A notification that *launched* the app is replayed to the first listener, so the route is not lost during start-up.
- Failures are logged through `dart:developer` and never thrown into the caller — a missing alert must not break the stock write that triggered it.

### Files (`impl/files/`)
- `PlatformFileService` — `pick()` through `file_picker` (bytes on every platform, including web) and `save()` through the share sheet on Android/iOS, a native save dialog on desktop and a browser download on web.

### Dev page
- `/dev/platform` (debug builds only — the W0 guard already blocks it in release) now runs each service by hand: scan, ask for notification permission, fire a low/out notification, pick a file, save a file, with the result shown on screen.

### Native configuration (outside my owned paths — see *Change requests*)
- `android/app/build.gradle.kts`: core-library desugaring + `desugar_jdk_libs:2.1.4` (required by flutter_local_notifications 22). Camera and POST_NOTIFICATIONS permissions come from the plugins' own manifests, so `AndroidManifest.xml` is untouched.
- `ios/Runner/Info.plist`, `macos/Runner/Info.plist`: `NSCameraUsageDescription`.
- `macos/Runner/{DebugProfile,Release}.entitlements`: `com.apple.security.device.camera` and `com.apple.security.files.user-selected.read-write`.

## Decisions I made (brief was ambiguous)
- **Two confirmations before a code is accepted.** "First stable code" needed a definition; two identical reads costs ~250 ms and removes nearly every misread.
- **Beep/vibrate use `SystemSound.play` + `HapticFeedback`** rather than an audio package — `pubspec.yaml` is frozen and these need no dependency.
- **`file_picker.saveFile` on desktop and web, share sheet only on Android/iOS** — the brief's split. file_picker 12 can also save on phones, but the share sheet is what a shop owner expects (send the backup to WhatsApp or mail it to themselves).
- **`supportsCamera` is a platform capability, not a device check.** A desktop browser with no webcam still reports true; the scan page then shows the translated "no camera" screen with manual entry. Detecting a camera up front would need an async permission probe on every screen that shows a scan button.
- **The deep link is wired in `notificationServiceProvider`**, not in `bootstrap.dart`, so nobody has to edit a lead-owned file. That does mean `platform_providers.dart` now imports `core/router/app_router.dart` (see *Follow-ups*).
- **Notification text is looked up per send** with `lookupAppLocalizations(effectiveLocale)`; the Android channel name is fixed at first init, since Android channels cannot be renamed afterwards.
- **Windows GUID** is a fixed constant for the app (`2f7c9b8e-…`); the app user model id varies per brand.

## Known issues / follow-ups
- **`platform_providers.dart` now imports `core/router/app_router.dart`** (for the tap deep link). Any test that touches a platform provider therefore compiles every feature's routes. It works, but if that becomes painful the wiring could move to a small `notification_deep_link.dart` started from `bootstrap.dart` instead.
- **Not verified on hardware** (nothing is available from this session): Android camera scan, USB scanner on Windows, notification tap on Android/Chrome/Windows, save/pick on Android/Chrome/Windows/macOS. `flutter build apk` cannot run here either — Gradle is blocked from writing its daemon registry. These are exactly the A5 acceptance boxes and need a person with the devices.
- **Web scanning needs HTTPS** (or `localhost`); on a preview channel that is already the case.
- The web plugin **replaces Flutter's own service worker** at runtime (upstream flutter#145828). Worth a second look with A7 when PWA offline caching is set up.
- macOS is sandboxed: `save()` writes only where the user picks in the dialog, which is what the entitlement I added allows.
